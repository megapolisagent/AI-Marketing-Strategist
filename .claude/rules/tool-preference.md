# Приоритет инструментов веб-доступа

> Какой инструмент брать по умолчанию для поиска и чтения веб-страниц.

## Правило

Для любого поиска в вебе и получения содержимого страницы — по умолчанию **Exa** (`mcp__exa__web_search_exa` для поиска, `mcp__exa__web_fetch_exa` для получения страницы), не встроенные `WebSearch`/`WebFetch`.

`WebSearch`/`WebFetch` — только когда:
- Exa вернула пусто или явную ошибку на этом конкретном запросе;
- конкретный скилл прямо предписывает другой инструмент для этого шага (пример: `.claude/skills/telegram-research/SKILL.md` требует `curl` через `Bash`, не Exa и не WebFetch, для чтения самих постов — это осознанное исключение, не отмена общего правила).

## Зачем

Проверено напрямую (владелица, 2026-09-14, `.claude/skills/competitive-brief/SKILL.md`, Research Sources): на официальном сайте застройщика (`alia.moscow/flats/`) `WebFetch` и ручные попытки давали пусто или домыслы на JS-рендеренных страницах — Exa отдала полную страницу с ценами. Тот же класс сайтов (каталоги объектов, JS-рендер) встречается в этой нише постоянно. `WebSearch` и `WebFetch` — общий инструмент харнесса без специализации под такие страницы; Exa в этом проекте уже подключена именно для этого и подтверждена рабочей.

## Как применять

До вызова `WebSearch`/`WebFetch` — спросить себя: пробовал ли Exa на этом запросе? Если нет — сначала Exa. Это касается директора и обоих поисковых субагентов (`competitor-researcher`, `market-researcher`) одинаково — предпочтение не зависит от того, кто делает запрос.

## Проверка цены/юнита перед публикацией карточки — Firecrawl, не Exa

Exa (`web_fetch_exa`) читает страницу как линеаризованный текст — на плиточной вёрстке (несколько карточек лотов рядом, пример: `alia.moscow/flats/`) это может склеить цену/площадь соседних юнитов в один поток без чёткой привязки к конкретному лоту. Для публикации карточки Avito неверная цена — не стилистическая ошибка, а прямой юридический риск (ст. 14.3 КоАП РФ, штраф для юрлица 100 000–500 000 ₽). На части JS-рендеренных сайтов застройщиков (пример: `dom-kinetik.ru/flat/realty/`) Exa и вовсе получает пустой результат — сервер не отдаёт данные без выполнения JS в браузере.

Для окончательной проверки конкретной цены/юнита перед публикацией — `mcp__firecrawl__firecrawl_scrape` c `formats: ["extract", "screenshot"]` и JSON-схемой полей (`rooms`/`area_sqm`/`price_rub` и т.п.), не текстовый `web_fetch_exa`. Схема возвращает каждый юнит отдельным объектом — цена и площадь физически не могут перепутаться между соседними карточками, и рендерит JS, где Exa получает пустоту. Скриншот в том же вызове — для визуальной сверки владелицей/CMO, не только доверия к тексту.

Проверено 2026-09-21 (Engineer, по прямому запросу CMO через владелицу): `alia.moscow/flats/` через Firecrawl с этой схемой вернул 24 юнита чистыми отдельными полями, без единого случая склейки. Ключ `FIRECRAWL_API_KEY` и MCP-сервер — тот же, что уже подтверждён рабочим у AI Avitolog и AI Legal Constructor, не новая интеграция.

Exa остаётся инструментом по умолчанию для обычного поиска/чтения (правило выше) — Firecrawl подключается точечно, на шаге проверки конкретной цены/юнита перед публикацией, не заменяет Exa везде.
