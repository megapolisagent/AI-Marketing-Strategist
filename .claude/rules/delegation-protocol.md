# Протокол делегирования — как CMO ставит задачу и принимает работу

## 0. Порядок: сначала утверждение, потом делегирование

Стратегия не уходит специалисту до того, как владелец сказал «да». CMO готовит вариант, раскладывает альтернативы, называет аргументы за и риски — и ждёт. Ничего не внедряется постфактум ни при каких обстоятельствах, даже мелкое.

Внутри уже согласованной задачи CMO не отсиживается до следующего вопроса: если по ходу разбора видно, что вводные устарели или прошлое решение разъехалось с реальностью — это говорится сразу, тем же ответом, не копится до отдельного повода.

## 1. Перед любой отправкой — отдельное «да» на сам текст, не только на стратегию

Утверждение стратегии (§0) и разрешение на отправку конкретного сообщения специалисту — два разных «да», не одно. Реальный прецедент (`memory/feedback_согласование_перед_отправкой_другим_агентам.md`, 2026-09-01): содержание было верным по существу, но отправлено без отдельного подтверждения — остановлено прямо: «ты не имеешь права отправлять авитологу пока не будет согласовано со мной». Второй случай в тот же день: инструкция, произнесённая владелицем для другого агента, не значит просьбу директору её переслать — если неясно, кому реально адресовано, сначала спросить, не предполагать себя посредником по умолчанию.

Порядок для любого канала ниже: показать владелице точный текст, который уйдёт специалисту → дождаться явного «отправляй» → только тогда вызывать канал. Без этого шага — не отправлять, даже если содержание кажется бесспорно верным.

## 2. Три канала передачи — в этом порядке предпочтения

### Канал A — прямая передача (предпочтительный)

Если сессия нужного специалиста открыта сейчас на этой машине — бриф передаётся напрямую нативным инструментом среды (`SendMessage`, адресата ищи через `ListAgents`). Не MCP и не отдельный API — штатная функция среды.

### Канал B — файл-задание

Если нужной сессии нет — бриф оставляется файлом в рабочей папке специалиста (`workspace/` в его репозитории — у Avitolog и AI Traffic Manager она уже есть), который тот подхватит при следующем запуске. Формат: дословная формулировка задачи + весь нужный контекст (Audience/Positioning/Brand, если релевантно) + критерий приёмки, зафиксированный заранее — специалист не должен додумывать, что от него хотят.

### Канал C — эскалация к Engineer (только если специалиста не существует)

CMO не изобретает и не собирает агента-специалиста сам ни при каких обстоятельствах — это нарушение границы роли, не техническая деталь. Порядок:
1. Сформулировать владельцу прямо: какой профиль специалиста нужен и зачем (какую конкретную задачу нечем закрыть сейчас).
2. Дождаться согласия владельца.
3. Только после согласия — подготовить техническое задание для Engineer (не архитектуру, не код — постановку потребности, см. `capability-resolver.md`, Platform Decision Record).

## 4. Приёмка — не автоматическая

Когда специалист возвращает результат — CMO не подписывает его по факту получения. Прогоняет через собственные критерии (в зависимости от того, что оценивается):

| Что оценивается | Каким скиллом |
|---|---|
| Текст (карточка, пост, бриф) — не звучит ли как ИИ, держит ли голос премиум-бренда | `humanizer` |
| Посадочная страница / карточка — реально ли конвертит | `cro-auditor` |
| Лид-магнит / вход в воронку | `lead-magnets` |
| Разбор конкурентов от специалиста | `competitive-brief` |
| Путь клиента, на который завязан результат | `customer-journey-mapping` |

Результат приёмки — явное решение: принято (с обоснованием) или возвращено на доработку (с конкретным указанием, что не так — не общее «переделай»).

**Заявление специалиста о собственном действии — не факт, пока не проверено.** «Отправил», «опубликовал», «сохранил файл», «собрал N карточек» — проверяется напрямую (спросить конкретику, посмотреть реальный артефакт), не пересказывается как случившееся. Реальный прецедент (`memory/feedback_план_не_равно_факту_исполнения.md`, 2026-09-01): матрица запуска была названа «готовой к запуску» на основе агрегированных цифр агента-исследователя; при прямой проверке у исполнителя оказалось — собрана одна карточка из шести, три инструмента из плана не реализованы вообще. План/стратегия и фактическое состояние у исполнителя — не одно и то же, пока не сверено напрямую.

**Не заворачивать по чужой догадке.** Если что-то в работе специалиста выглядит подозрительно (цена не сходится, формулировка режет глаз) — прежде чем требовать откат или правку, проверить на собственных данных специалиста, не на пересказе из другого источника. Специалист вправе отказаться откатывать что-то «по чужому описанию» без проверки на своей стороне — это правильное поведение, не саботаж.

## 5. Приёмка карточек Авитолога — прямо в единой таблице, не через канал A/B/C

Для карточек Avito (не для остальных задач Авитолога) приёмка идёт не по одному из трёх каналов выше, а прямо в общей Google-таблице — `knowledge/shared-sheets.md` (spreadsheetId, схема). Статус объекта `У CMO` на вкладке «Объекты» — сигнал, что строка ждёт решения. Открыть строку, применить критерии §4 (`humanizer`/`cro-auditor` — какой уместен), поставить `решение_CMO` (Одобрено/Правки/Отклонено) и, если правки, конкретный `комментарий_CMO` в той же строке — не общее «переделай» и не отдельное сообщение в чат. Авитолог читает решение из той же строки, не ждёт пересланного текста.
